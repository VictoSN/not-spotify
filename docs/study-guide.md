# Not-Spotify — Codebase Study Path (Interview / Presentation Prep)

## Context
You (a 3-person team: TP073309 Marvind, TP073945 Stanlie, TP072895 Victorio) built **Not-Spotify**, a
full-featured music-streaming platform, and deployed it on AWS for the CT071-3-3-DDAC cloud module. You
need to be able to answer *any* question a lecturer/interviewer throws at you — about the app itself and
about the cloud architecture. This is a **5-day study path**, ordered app-first, **AWS last** (so the
cloud story sits on top of a solid understanding of what's actually running).

**How to use this:** each day has 2 sessions (~1.5–2h each). For every session: (1) read the listed files
with the app open beside you, (2) learn the key concepts, (3) rehearse the Q&A out loud. The **★ questions
are the ones most likely to be asked** — make sure all three of you can answer those.

**The stack in one breath:** React 18 + TypeScript + Vite SPA (Zustand state, React Router, SignalR client,
Tauri desktop shell) → talks to an ASP.NET Core 8 Web API (EF Core 8 + PostgreSQL, ASP.NET Identity + JWT,
SignalR hubs) → deployed on **AWS ECS Fargate** behind an ALB, data in **RDS PostgreSQL**, media in **S3**,
SPA served via **CloudFront + Route 53**, catalogue search on **Amazon OpenSearch**, a **serverless upload
microservice** (API Gateway + Lambda + S3), monitored with **CloudWatch + X-Ray**, payments via **Stripe**.

## DAY 1 — Foundations & the Big Picture

### Session 1.1 — Repo map & the stack
**Goal:** Be able to draw the whole system on a whiteboard and say what every box does.
**Read:** `README.md` (top → "Architecture & Conventions"); `backend/src/NotSpotify.Api/Program.cs`
(skim — this is the wiring hub); top of `frontend/src/main.tsx` and `frontend/src/App.tsx`.
**Key concepts:**
- Three runtime surfaces, **one React bundle**: browser tab, installed PWA, Tauri desktop shell
  (`frontend/src/utils/platform.ts` → `isDesktop()`). Same code, different host.
- Monolith API + one serverless microservice. Everything is in the ASP.NET monolith *except* the
  presigned-upload Lambda — know why (that's Day 5).
- Client never holds business logic that matters: auth, plan gating, ownership all enforced server-side.

**★ Q&A:**
- *"Walk me through your architecture."* → Users hit `not-spotify.lol` (Route 53 → CloudFront → S3 static
  SPA). The SPA calls `api.not-spotify.lol` (ALB → ECS Fargate container running ASP.NET Core 8). The API
  uses RDS PostgreSQL for relational data and a private S3 bucket for media; audio/images stream to the
  browser directly from S3 via short-lived presigned URLs. Search runs on OpenSearch. Uploads go through a
  serverless path (API Gateway + Lambda). Stripe handles payments. CloudWatch + X-Ray monitor it.
- *"Why a SPA + separate API instead of server-rendered pages?"* → Clean separation, the same API serves
  web + PWA + desktop, and the static SPA is cheap to serve from S3/CloudFront (no compute).

### Session 1.2 — Request lifecycle end-to-end
**Goal:** Trace one action (e.g. "play a track") from click to sound.
**Read:** `frontend/src/services/api.ts` (the axios client + auth interceptor + refresh mutex);
`frontend/src/stores/playerStore.ts` (skim); `backend/src/.../Controllers/TracksController.cs`;
`backend/src/.../Services/MediaMapper.cs` (how a DTO gets its `audioUrl`).
**Key concepts:**
- Every request carries a short-lived JWT access token (`Authorization: Bearer`) attached by the axios
  interceptor; the token lives in memory (`window.__authToken`), not localStorage.
- The API returns DTOs (not EF entities). `MediaMapper` turns an S3 object key into a **presigned GET URL**
  at response time — so the browser streams audio straight from S3, bypassing the container.

**★ Q&A:**
- *"What happens when a user plays a song?"* → The player store calls the API for the track; the API returns
  a DTO whose `audioUrl` is a presigned S3 URL; the audio element streams directly from S3; a play event is
  written to RDS to feed recommendations.
- *"Where does the audio actually come from — your server?"* → No. Only a presigned URL is generated by the
  server (a local signature, no data). The bytes go browser ↔ S3 directly. That's what keeps a music app
  affordable on one small container.

## DAY 2 — Backend Deep Dive (ASP.NET Core + data)

### Session 2.1 — API structure, DI, EF Core
**Goal:** Explain how the backend is organised and how it talks to Postgres.
**Read:** `Program.cs` (properly this time — DI registrations, middleware order, `MigrateAsync`);
`backend/src/.../Data/AppDbContext.cs`; one representative controller
(`Controllers/PlaylistsController.cs`); the `Migrations/` folder listing.
**Key concepts:**
- **Controllers → Services → DbContext**. 40 controllers (incl. 14 admin), 38 services. Services are
  registered in `Program.cs` (singleton/scoped). `IStorageService` is the key abstraction (S3 ↔ Local
  chosen by config).
- **EF Core 8 + Npgsql**. 46 entity models, 37 hand-authored migrations. `MigrateAsync()` runs on startup;
  migrations are idempotent (`CREATE … IF NOT EXISTS` guards) because the DB is shared by the team.
- Configuration flows from `appsettings.json` + environment variables (12-factor). The connection string,
  JWT key, Stripe keys, S3 bucket, OpenSearch endpoint all come from config.

**★ Q&A:**
- *"How does your app store data?"* → EF Core 8 over PostgreSQL (RDS in prod). Code-first with migrations
  that auto-apply on container start.
- *"How do you swap S3 for local disk?"* → Both implement `IStorageService`; `Program.cs` registers S3 when
  `S3Storage:BucketName` is set, else `LocalStorageService`. No code change — just config. (Great example of
  the dependency-inversion principle to cite.)

### Session 2.2 — Auth, security, RBAC
**Goal:** Own the security story — it's the strongest part of the codebase.
**Read:** `Controllers/AuthController.cs` (login, refresh, logout, the refresh cookie); `Services/TokenService.cs`;
`Program.cs` JWT bearer config (incl. the SignalR `?access_token=` handling); the rate-limiter setup.
**Key concepts:**
- **Two-token model:** a short-lived JWT access token (~15 min, in memory) + a **rotating refresh token** in
  an HttpOnly, Secure, SameSite=None cookie (path `/auth`). Each `/auth/refresh` issues a *new* refresh
  token (single-use) with a 60s grace window; a **cross-tab Web Locks mutex** (`api.ts`) serialises
  refreshes so two tabs don't race and log each other out.
- **ASP.NET Identity** for password hashing. **RBAC**: roles in the JWT (`ClaimTypes.Role`); a master-admin
  tier + a `PendingActions` approval queue so no single admin can self-escalate.
- **Rate limiting** (`auth` 20/min/IP, `chat-send` 20/10s/user) → JSON 429 + `Retry-After`.
- reCAPTCHA gate on registration (skipped in the desktop webview).

**★ Q&A:**
- *"How do you keep users logged in securely?"* → Short-lived access token in memory + rotating refresh
  cookie. The access token can't be stolen from localStorage (it isn't there); the refresh cookie is HttpOnly
  so JS can't read it. Rotation means a stolen refresh token is single-use.
- *"Two browser tabs, both refresh at once — what happens?"* → A browser-wide Web Locks mutex serialises them,
  so the second waits and sees the token the first set. Without it they'd race on the single-use token and one
  tab would get logged out.
- ★ *"How do you stop an admin abusing their power?"* → Two-tier RBAC: a regular admin's grant/revoke enqueues
  a `PendingAction` that a master-admin must approve.

## DAY 3 — Frontend Deep Dive (React + player)

### Session 3.1 — React app, routing, state
**Goal:** Explain how the SPA is built and how state is managed without Redux.
**Read:** `frontend/src/router/index.tsx` (route tree, `ProtectedRoute`, subdomain handling);
2–3 stores — `stores/authStore.ts`, `stores/libraryStore.ts`, `stores/playerStore.ts` (skim);
`frontend/src/components/layout/` (Sidebar, TopBar).
**Key concepts:**
- **Zustand** for state (15 stores), not Redux — simpler, hook-based (`useAuthStore((s) => s.user)`).
  Each store owns one domain (auth, library, player, chat, friends, notifications, theme, locale…).
- **React Router** with nested routes; `ProtectedRoute` gates authed pages; a subdomain check routes
  `account./support./download.` to the right section (same bundle, different host).
- **Vite** build; content-hashed assets; a service worker for PWA + offline. TypeScript throughout.
- i18n is a tiny hand-rolled `useTranslation` hook over a `translations.ts` map (en/es/fr).

**★ Q&A:**
- *"Why Zustand over Redux?"* → Much less boilerplate for a solo/small team; selector-based subscriptions
  keep re-renders tight; no reducers/actions ceremony. Each domain is one small store.
- *"How do you protect routes?"* → A `ProtectedRoute` wrapper checks the auth store; unauthenticated users
  are redirected to `/login` (with a validated `?next=` return path — see the account-handoff work).

### Session 3.2 — The player, audio, offline, PWA/desktop
**Goal:** Explain the hardest client engineering — audio playback and offline.
**Read:** `frontend/src/services/audioEngine.ts` (two-deck engine); `frontend/src/services/offlineAudio.ts`
+ `frontend/public/sw.js` (Range reconstruction); `frontend/src/utils/platform.ts`; `frontend/src-tauri/`
(Tauri config — `frontendDist` bundles the SPA).
**Key concepts:**
- **Two-deck audio engine**: two `HTMLAudioElement`s (not Web Audio — `MediaElementSource` taints
  cross-origin S3 audio) for gapless/crossfade. The player store decides *what* plays next; the engine only
  overlaps for crossfade. `mediaSession` handlers are registered once (re-registering broke Edge PiP).
- **Offline (Premium):** a track is stored in Cache Storage / Tauri FS; the **service worker reconstructs
  HTTP 206 partial responses** from the cached body so seeking works offline. This is why the S3 read CORS
  rule must expose Range headers.
- **PWA + Tauri:** installable PWA with an offline app shell; Tauri wraps the *same* frontend in a native
  window (bundles `dist/`, so desktop changes need a `tauri build`).

**★ Q&A:**
- ★ *"How does offline playback work?"* → The audio file is cached client-side; a service worker intercepts a
  dedicated path and rebuilds byte-range (206) responses from the cache, so seeking/resume behave exactly like
  online. Premium-gated server-side.
- *"Why not Web Audio API for crossfade?"* → `MediaElementSource` taints cross-origin S3 streams (breaks
  playback), so we use two `<audio>` decks and overlap them instead.

## DAY 4 — Feature Systems (the "wow" features to demo)

### Session 4.1 — Search, Playlists, Social (real-time)
**Goal:** Explain the three headline systems.
**Read:** `Services/OpenSearchService.cs` (SigV4 wiring lines ~96–113, `TextQuery` lines ~319–336);
`Controllers/SearchController.cs` (OpenSearch-or-SQL fallback); `Services/SmartPlaylistService.cs` +
`Controllers/PlaylistsController.cs` (visibility); `Hubs/ConnectHub.cs`, `Hubs/PresenceHub.cs`,
`Hubs/SessionHub.cs` + `Program.cs` MapHub lines.
**Key concepts:**
- **Search = Amazon OpenSearch**, not SQL. Five indices (tracks/artists/albums/playlists/videos) queried
  **concurrently** (`Task.WhenAll`). Each index runs a boolean `should` of **fuzzy** (`Fuzziness.Auto` →
  "nirvna" finds Nirvana) + **prefix** (`BoolPrefix` → as-you-type). Track scores blend text relevance with
  `log10(2 + playCount)`. Auth is **IAM SigV4** (no credentials in the app). Graceful **SQL fallback** when
  the endpoint is unset. *(Known gotcha to mention: the SigV4 single-string ctor takes a service name, not a
  region — passing the region 403s everything.)*
- **Smart playlists**: rules (genre/min-rating/min-plays/added-within-days) stored as **JSONB**, evaluated on
  open, so the playlist maintains itself. **Profile presence = public visibility**; **Library = saved
  playlists** — two separate concepts (this was a real bug you fixed).
- **Real-time via SignalR**: 3 hubs — Presence (Friend Activity), Session/Jam (listen-along), Connect
  (multi-device transfer). WebSocket handshakes can't send headers, so the JWT arrives as `?access_token=`,
  accepted only on `/hubs/*`. Per-user groups → messages reach only that user's devices; `OthersInGroup`
  avoids state feedback loops.

**★ Q&A:**
- ★ *"How does search tolerate typos and feel instant?"* → One OpenSearch query per index (run concurrently)
  combining fuzzy matching (edit distance) with prefix matching (as-you-type); popularity breaks ties.
- ★ *"How do you authenticate to OpenSearch?"* → IAM SigV4 signing with the ECS task role from the default
  credential chain — no username/password/API key anywhere in the app.
- *"How does listen-along / multi-device work?"* → SignalR hubs; each connection joins a group keyed to its
  user id; transfer/state messages are routed only within that group.

### Session 4.2 — Media pipeline, uploads, billing
**Goal:** Explain how files move and how money moves. Sets up Day 5.
**Read:** `Services/S3StorageService.cs` (`BuildUrl` presigned GET, `EnsureBrowserCorsAsync`);
`Controllers/MeUploadsController.cs` (`Complete` endpoint); `frontend/src/services/uploadService.ts`
(presign → direct S3 → complete, with fallback); `Controllers/BillingController.cs` +
`Services/StripeBillingService.cs`.
**Key concepts:**
- **Media delivery:** private bucket (Block Public Access on) + presigned GET URLs. Bucket CORS lives in
  **code** (`EnsureBrowserCorsAsync`) because `PutBucketCors` replaces the whole config — console edits get
  wiped.
- **Uploads (the serverless story):** browser asks the Lambda for a presigned **POST** (POST, not PUT, so
  `content-length-range` caps size); uploads straight to S3; then calls `POST /me/uploads/complete`, which
  re-verifies ownership (prefix), existence + size (HeadObject), rejects replays (409). Frontend **falls back**
  to the old multipart path if the presign service is down. Full detail is Day 5.
- **Billing:** Stripe Checkout (hosted); card data never touches your servers; the plan is granted via
  `/billing/sync` (webhook path). Premium capabilities flow to the client in the JWT — enforced backend-first.

**★ Q&A:**
- ★ *"How do users upload audio without overloading your server?"* → They don't upload *to* the server. The
  browser gets a one-time signed S3 POST policy from a Lambda and uploads directly to S3; the server only
  records the finished object after verifying it. (This is the Task 2 serverless deliverable.)
- *"Is payment secure?"* → Card data goes to Stripe's hosted checkout, never our servers; we grant Premium
  server-side and gate features in the backend.

## DAY 5 — AWS / Cloud & Monitoring (LAST)

### Session 5.1 — Deployment topology + the serverless microservice
**Goal:** Own the cloud architecture — the marked part of Task 2.
**Read:** `docs/aws-lambda-setup.md`; `docs/ecs-…` / `docs/aws-rds-setup.md` / `docs/aws-s3-setup.md`;
`serverless/uploads-presign/lambda_function.py`; `serverless/deploy-lambda.ps1`; `frontend/deploy-frontend.ps1`.
**Key concepts (memorise the topology):**
- **Compute:** ASP.NET API as a container on **ECS Fargate** behind an **Application Load Balancer** (HTTPS),
  image pulled from **ECR**. Region **ap-southeast-1**.
- **Data:** **RDS PostgreSQL** (db.t3.micro). **Media:** private **S3** bucket. **Static SPA:** S3 + **CloudFront**
  + **Route 53** (ACM wildcard cert). **Search:** **OpenSearch** domain.
- **Serverless upload path (Task 2 core):** **API Gateway (HTTP API)** → **Lambda** (`generatePresignedUrl`,
  Python 3.12) → **S3**. The Lambda **verifies the app's own HS256 JWT in-process** (API Gateway's built-in
  authoriser only speaks OIDC/JWKS, which the app doesn't use) with an **algorithm allowlist** that defeats the
  `alg:none` forgery. It signs a presigned **POST** policy; the browser uploads directly to S3.
- **Least privilege = blast radius:** the Lambda's role has `s3:PutObject` on `uploads/*` **only** — because a
  presigned URL inherits the signer's permissions.
- **Cost honesty:** it does *not* reduce the bill at this scale (Fargate runs 24/7; Lambda+API GW are free-tier).
  The wins are **isolation, independent deployability, and a tighter IAM boundary** — say this, don't claim a
  cost saving a marker can disprove.

**★ Q&A (these are the exam):**
- ★ *"Explain your serverless architecture and which AWS services it integrates."* → API Gateway + Lambda +
  S3. Browser → `POST /presign` (API GW) → Lambda verifies the JWT, signs a size-capped S3 POST policy →
  browser uploads straight to S3 → API records the object after a HeadObject check. Satisfies Part 2 (serverless
  working with S3).
- ★ *"Why is there no S3 node on the X-Ray service map?"* → Generating a presigned URL is a **local
  cryptographic signature**, not an S3 API call — so there's nothing downstream to trace. The map proving that
  is the architecture working.
- ★ *"What changed from Task 1 to Task 2?"* → Task 1: uploads streamed multipart *through* the ECS container
  (50 MB cap, a container constraint). Task 2: the container leaves the data path — browser → S3 directly via a
  Lambda-signed policy (100 MB, enforced by S3), with independent scaling and a scoped IAM role.
- *"Why put Lambda outside the VPC?"* → It only signs URLs (no DB/VPC resources needed), so no VPC attachment
  means no cold-start ENI penalty. (Also the honest trade-off: the JWT signing key now lives in two places —
  ECS task def + Lambda env — and must be rotated together.)

### Session 5.2 — Monitoring, security decisions, mock Q&A
**Goal:** Close the loop on Part 3 (monitoring) and do a full mock.
**Read:** `docs/task2-serverless-discussion.md`; `Services/XRayHttpTracingHandler.cs` +
`XRayHttpMessageHandlerBuilderFilter.cs` (backend X-Ray is now instrumented); the Reflection + Findings
sections of the report.
**Key concepts:**
- **CloudWatch** = "is it healthy and how much" (metrics/logs/alarms): ECS CPU/memory (Fargate gives task-level
  metrics with no agent), RDS, Lambda (invocations/duration p50-p95/errors/throttles), API Gateway (count,
  latency, 4XX/5XX). **X-Ray** = "where did the time go in one request" (traces + service map).
- Reading the graphs like an engineer: API Gateway **4XX is healthy** here (each unauthenticated presign is a
  401 — the auth layer visibly working); a Lambda **error** metric excludes 401/413/422 (those are successful
  invocations returning an error *response*); CloudWatch is the only way to observe a Lambda (no machine to SSH
  into) — serverless removes the server, not the need to observe it.
- **CORS everywhere:** three surfaces (API Gateway CORS for the presign call; the bucket CORS for the direct
  upload; the API's own CORS). Know why each exists.

**★ Mock questions to rehearse cold:**
- "Why CloudWatch for Lambda and not just the computer?" · "Show me least privilege in your design." ·
  "How would you cut the AWS bill?" (scale ECS to 0 off-hours, stop RDS, Fargate Spot, ARM/Graviton, drop the
  ALB only if the API moved off ECS) · "What would you improve given more time?" (orphaned-upload cleanup via
  S3 lifecycle; a zero-hit SQL fallback for the empty-index failure; move ZIP downloads to Lambda+SQS).
